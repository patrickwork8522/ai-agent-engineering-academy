  1. Define the unknown: a model limitation, a data failure, a software pattern or a business decision? Write the specific question.
  2. Locate primary evidence: official docs, a peer-reviewed paper, source code, a benchmark specification, or a first-party incident analysis.
  3. Reproduce the mechanism: try an official example, inspect a trace or create a tiny synthetic experiment.

01 · What is an agent, and who actually runs a tool?

A language model predicts its next output from context. An agent is a software system that lets a model propose actions, calls tools through application code, observes results and decides what to do next. A model does not inherently have Databricks or Oracle access. A developer defines functions and permissions that the application can execute.

Picture the trading director asking for a sales check. The agent selects get_sales(start, end, stores), the host validates arguments and sends a read-only query, the data system returns rows, and the model writes an explanation. Errors can occur at each boundary. A successful tool execution proves that a query ran; it does not prove that the chosen dates answer the director's question.

Request → Model chooses tool + dates → Host validates access → Warehouse returns rows → Agent interprets output → Policy checks recommendation → Human approves action

Transfer question: Which steps should log input/output, and where would you block an unauthorized price change?

02 · Data contracts, grain and time-window validity

Business metrics have precise definitions. “Sales” might mean gross orders, net completed transactions, values after returns, or store-local transactions converted to GBP. A table also has a grain: one row might represent a transaction, store/hour, or store/day. A query can be syntactically correct while measuring the wrong thing.

Comparisons need equivalent populations and windows. If a Monday's first 14 hours (£785k) are divided by the previous Monday's full-day sales (£1.02m), the change is (785−1020)/1020 = −23.0%. But when the prior Monday is restricted to the same hours (£770k), the change is (785−770)/770 = +1.95%. Neither observation alone establishes why anything happened.

Compare apples to apples: 1. Same metric definition and currency 2. Same durations, time zones and trading hours 3. Same comparable stores/products 4. Loaded partitions and returns accounted for 5. Sufficient baseline for seasonality and uncertainty

Practice: Write a validation rule that would detect mismatched comparison intervals before allowing an alert.

03 · Fabrication, grounding and unsupported conclusions

A model can hallucinate nonexistent facts, but a more subtle failure occurs when it cites authentic facts and draws an invalid conclusion. Giving an agent database access is called grounding when its claims rely on evidence, but the evidence must also be relevant, fresh and correctly interpreted. Stating “confidence: high” is not the same as having a calibrated, independently tested likelihood that a claim is correct.

To improve trust, attach provenance to every important claim: source, query identifier, parameters, timestamp, data-quality state, assumptions and uncertainty. Calculations with known definitions should be checked deterministically. The agent should be able to say “insufficient evidence” when business impact or causes remain unknown.

Practice: Rewrite the alert as an observation that does not pretend to know the cause or the best response.

04 · Evaluation, traces and production reliability

Evaluations (evals) are tests that compare actual agent behavior to an expected outcome. For a database query you may test syntax, schema and permissions. For an agent, evaluate the entire sequence: selected tools, arguments, intermediate interpretations, final claims and permitted actions. A trace is the record of those steps.

One good demo is not reliability evidence. Build cases for mismatched time windows, partial data, missing partitions, contradictory results, tool timeouts and malicious instructions in retrieved content. Measure task correctness, safety, cost, latency, repeatability and appropriate refusal separately.

Worked evaluation: Given the partial-Monday incident, require the agent to flag incomparable windows, request aligned data, withhold a chain-wide discount recommendation, and trace its reasons. Fail if it makes the original unqualified claim—even if the database request returns OK.

05 · Consultant thinking: issue trees and recommendations

A consulting case is not solved by repeating a technical error message. Define the business decision: Should we authorize an emergency 15% chain-wide discount? Then form testable branches: (1) Is the measured decline real? (2) What caused it? (3) Would the proposed action improve profit versus alternatives? (4) Who has authority to act? For each branch, identify specific evidence that could prove your hypothesis wrong.

A blanket discount can increase units sold while reducing gross margin or causing stockouts. Even a genuine sales decline does not automatically support discounting. The consultant separates observation from causal explanation from action.

Worked recommendation: “Do not authorize the discount. The 23% alert compared an incomplete Monday with a completed Monday. Matched-hour sales are approximately 1.95% higher, although we have not checked seasonality or data completeness. Validate comparable-store performance, then have Trading and Finance assess margin implications before considering a promotion.”

Practice: Name one alternative hypothesis, the evidence to check it, and the cost of acting too early.

Exercise A · Build an issue tree

Write three independent questions you must answer before recommending a discount, and name the evidence for each.

Hint

Separate metric validity, explanation of any real decline, and action economics.

Worked solution and rubric
  1. Validity: Are intervals and store cohorts aligned? Check query parameters, table metadata and data-load watermarks.
  2. Causality: If a real movement remains, where and why? Compare stores and categories; check promotions, weather, availability and returns.
  3. Decision: Will a discount improve margin and inventory outcomes? Check elasticities, contribution margin, constraints and alternatives.

A strong response proposes disconfirming evidence, not only a list of plausible reasons.

Exercise B · Design three guardrails

Specify three machine-checkable rules, with the condition for stopping or escalating an agent run.

Hint

Think metric-contract validation, feed completeness and approval for consequential actions.

Worked solution and rubric
  1. Reject comparisons with unequal windows, incomparable cohorts or inconsistent units.
  2. Require a freshness/completeness watermark; label incomplete periods and require matched-hour checks.
  3. Require business-owner approval plus documented gross-margin impact before any price change.

Advanced: record every failed rule in a trace and include it in an automated evaluation dataset.

Exercise C · Write a decision memo

In 120–220 words, provide a decision, evidence, uncertainty, immediate follow-up and lasting system change.

Hint

Lead with the decision and numbers. Explain what is known and what still needs checking.

Worked solution and rubric

Decision: Pause the emergency discount. Evidence: The initial 23% decline compared 14 hours of Monday sales to a 24-hour Monday baseline. A matched-hours calculation finds £785k versus £770k, approximately +1.95%. Uncertainty: Store mix, seasonality, data completeness and profitability remain unverified. Immediate action: Confirm freshness and comparable-store trends, then request Trading/Finance review. System change: Enforce a metric contract, window validations, trace logging, regression evaluations and human approval for pricing changes.
