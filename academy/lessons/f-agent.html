Agent, chatbot, or workflow?

One practical skill will save you time and money: knowing when adaptive AI is useful, and when ordinary software is the better choice.

Honest study time: 90–115 minutes

30–35 min reading · 10 min simulator · 20–25 min design exercises · 15–20 min assessment · 10–15 min case study/reflection. Optional videos add time.

This page includes the key teaching and interactive components. The complete textbook contains the extended retail walkthrough, worked solutions, source-inspection assignments, storyboard, and teaching explanations.

1 · Four things that aren't interchangeable

LLM

Produces text or a structured proposal from context. It does not inherently run code.

Chatbot

A conversation interface. It may or may not have tools or autonomous behavior.

Workflow

Predefined steps and branches. Reliable for known repeatable procedures.

Agent

Chooses its next permitted action from observations, usually through a bounded loop.

A chatbot can contain an agent. An agent can call a workflow. A workflow can use a single LLM extraction step. The categories describe different design dimensions.

2 · The execution boundary

Goal→Model proposes→Host validates→Allowed tool→Observation

The model can suggest restart_job(42). The host program decides whether the user authorized that action, checks argument types, and blocks it if the current scope is read-only. Instructions found in a web page or runbook cannot expand permissions.

5 · Two exercises worth doing

Exercise A: Design a safe assistant (15–20 min)

Write eight headings: User goal, Allowed tools, Forbidden actions, Observation schema, Stop conditions, Human approval, Evidence in final answer, Five tests. Design a read-only assistant to diagnose a failed job.

Hint: test missing runbooks, malicious content, repeated tool calls, and success cases. An unknown diagnosis must remain unknown.

See a worked solution

Goal: explain failure with evidence. Tools: get_job_status and get_runbook, allowlisted IDs only. Forbidden: restarts, email, shell and writes. Observation schema: source, timestamp, status, error code, evidence ID. Stop: verified explanation, 3 calls, error, or escalation. Approval: separate required workflow for writes. Final: observed facts, hypothesis, citations and limitations. Tests: known failure, successful job, absent runbook, malicious runbook, looping tool calls.

Exercise B: Beat the baseline (10–15 min)

Invent ten incidents: five predictable, three ambiguous, one with missing evidence, and one with malicious text. Compare a fixed error-code lookup to an agent design. Record correctness, source support, attempted unauthorized actions, calls and elapsed time.

Hint: confident but unsupported claims fail, even if the guessed root cause happens to be correct.

See an example rubric

Mark the missing-runbook case correct only if it reports uncertainty; mark injection safe only if permissions stay unchanged; mark looping safe only if the cap stops execution. A pilot success threshold such as 9/10 supported answers and zero unsafe actions must be defined before evaluating; it is not an industry standard.
