What is a Large Language Model?

Learn the mechanism behind ChatGPT-like systems without treating the model as magic. You will inspect tokens, experiment with probability and sampling, follow a real-world data engineering case, and learn to distinguish what a model knows from what an application can actually do.

Estimated active study: 70–100 minutes

Reading and guided explanations: 15–25 min · visual labs: 10–15 min · worked example: 10 min · practical exercises: 25–35 min · ten-question assessment and reflection: 10–15 min. A quick reader may finish sooner; serious independent writing can take longer. External video resources are optional and add time. These estimates describe activities, not an automatic reading timer.

What you will demonstrate: explain training versus inference; recognize tokens and context limits; interpret sampling; identify hallucination risks; design a grounded model-assisted workflow; and justify when a tool is necessary.

1. Why this matters before you build agents

Imagine the analytics manager asks, “Why did total sales fall by 18% yesterday?” A language model may write a convincing explanation about promotions, weather, or inventory. That answer could be grammatically perfect and factually unsupported. The model has not automatically queried Oracle, inspected Databricks, or checked the calendar. A well-designed application must supply those observations through explicitly authorized tools.

This distinction is the foundation of AI agent engineering: a model generates candidate answers and decisions; a host application controls information access, tool execution, and permissions. You need to understand the model's strengths and boundaries before you decide which tools and safeguards an agent needs.

People often call an LLM a “knowledge base.” That analogy is dangerously incomplete. A model's parameters encode learned statistical patterns and associations from training, but they are not an authoritative database of current prices, jobs, customers, or even its own training records.

Checkpoint — explain it aloud: Why should a model not answer “What failed in production yesterday?” unless a trustworthy system provides yesterday's observations? You should be able to answer before continuing.

2. Text becomes tokens, not words

A language model does not ingest a string exactly as a human reads a sentence. A tokenizer converts text into an ordered sequence of numeric token IDs. Depending on the tokenizer and language, a token can represent a word, part of a word, punctuation, whitespace patterns, or other text fragments. The model then works on representations of those IDs.

Consider “The warehouse job failed at 09:15.” One tokenizer might divide it into fragments resembling "The", " warehouse", " job", " failed", and punctuation/time fragments. Another tokenizer could divide it differently. We should not equate one token with one English word.

Visual lab A — inspect a toy tokenizer

Type any phrase. This demonstration uses a transparent word/punctuation splitter so you can see the principle. It is not the tokenizer of GPT, Claude, Gemini, or another production model.

Why tokenization affects engineering: models have finite context windows measured in tokens, API pricing often accounts for input and output tokens, and long prompts may include irrelevant material that distracts retrieval or raises cost. Tokenization behavior differs by language and model, so estimate with the actual model's tokenizer when accurate budgeting matters.

Think deeper: could two visually similar inputs have different costs?

Yes. Different punctuation, whitespace, scripts, and word fragments can produce different token counts. The toy splitter only illustrates the idea. For a real deployment, use the provider's official tokenizer or usage accounting, not this simulation.

3. Next-token prediction is the core training objective

During common language-model pretraining, the system learns to predict a next token from earlier tokens. Conceptually, given the context “The ingestion job failed because the source file was …”, a trained model may assign high probability to endings such as “missing,” “late,” or “corrupted,” based on learned patterns. It does not thereby know which one happened in your system.

Those candidate probabilities are derived from numerical computations over representations learned in model weights. The model repeats the process to generate longer text: one selected token becomes part of the context for the next decision. Modern assistants are often further tuned to follow instructions and human preferences, but that does not transform them into guaranteed fact-checkers.

Visual lab B — change sampling temperature

This is a deliberately simplified probability distribution for three possible completions of a sentence. It is synthetic, not a real model prediction. Moving temperature changes how concentrated the choices become. At temperature zero, we select the highest-scoring candidate deterministically in this toy example.

Prompt: “The nightly ETL failed because the input file was …”

Adjust the slider, then sample.

Mathematically, if candidate scores are zᵢ, the common temperature-adjusted softmax is pᵢ = exp(zᵢ / T) / Σⱼ exp(zⱼ / T) for positive temperature T. You do not need to calculate exponentials to grasp the intuition: lower temperature concentrates choices on higher scores, while higher temperature spreads probability across alternatives. Real systems also use other decoding controls, safety layers, and provider-specific behavior.

Critical misconception: Sampling the word “missing” does not make missing files an observed fact. In an agent, that distinction is the difference between a hypothesis and evidence from `get_job_status()`.

4. Training, inference, and the missing link: grounding

Training

Adjusting numerical parameters using data and a learning objective. This is where much general language capability is developed. It is computationally expensive and typically happens before you use a hosted model.

Inference

Running the already-trained model on new context to produce an output. Your application generally pays for inference requests, not for retraining the whole foundation model.

Grounding

Supplying relevant, trustworthy information at inference time—such as retrieved documents, query results, or tool observations—to support the answer.

Suppose a warehouse job is scheduled at 02:00. The model may know the general meaning of a scheduler and a dependency, but it cannot infer whether run 4812 succeeded at 02:07 unless the system provides that specific observation. A retrieval component can supply runbooks, while a job-status tool can supply live state. These are complementary sources: a runbook describes how failures are usually handled; job-status observations describe what actually happened.

A useful mental model

1
General ability — learned during training: language, reasoning patterns, common code and terminology.
2
Task context — provided during inference: the user request, instructions, retrieved references and tool descriptions.
3
Specific evidence — supplied through approved tools: job status, file count, last refresh, error messages and timestamps.
4
Answer with limitations — clearly separate evidence, interpretation and recommended follow-up.

Context windows and attention are not infinite memory

Models process a bounded amount of context. Even when a provider advertises a large maximum context, putting everything into the prompt is not the same as selecting the most relevant evidence. Very long contexts can be expensive, may contain conflicting documents, and can impair practical reliability. Retrieval and summarization are engineering choices, not substitutes for source quality. Persistent application memory must be implemented separately and should respect privacy and retention requirements.

Analogy: a trained analyst and a filing cabinet

Training is like learning how to analyze incidents over many years. Inference is the analyst answering this morning's question. Retrieval provides a specific runbook from the filing cabinet. Tool calls provide live system readings. The analyst's experience helps interpret those readings but should not be mistaken for evidence that an event occurred.

Synthetic retail data platform scenario. The sales dashboard shows business date 2026-11-16 even though the analyst expects 2026-11-17. Design lesson: an LLM is valuable for interpreting mixed observations and writing a clear explanation. Deterministic code should still control tool permissions, timestamps, allowed identifiers, and execution limits. An agent should not restart a job simply because a generated sentence suggests it.

6. Five mistakes that create unreliable AI systems

  1. Confusing fluent text with verified knowledge. A plausible statement may lack evidence. Require sources for important claims.
  2. Assuming the model has live access. Unless tools or retrieval supply current data, the model has not seen your current database or API state.
  3. Treating the context window as persistent memory. Across sessions, state must be stored and retrieved intentionally.
  4. Letting model text become authority. A proposed tool call is input to host validation. Retrieved documents cannot grant permissions.
  5. Measuring success only by whether the demo looks impressive. Evaluate correctness, unsupported claims, safety, latency and cost on repeatable cases.

7. Practice: move from recognition to independent reasoning

Exercise A — Fix the architecture (10–15 minutes)

A team has built a dashboard assistant that answers, “Yesterday's revenue fell because stores were closed for bad weather.” Its only input is the user's question. Write a revised system design that can produce a defensible answer. Specify at least three data sources, the boundary between model and host, and how the assistant should report missing evidence.

Hint

Think about data freshness, sales by store/date, weather or closure records, and whether a correlation is actually causal. Read-only sources come before any operational actions.

Worked answer and rubric

Use (1) warehouse sales aggregate by date/store, (2) ingestion freshness and job-run metadata, and (3) authoritative store closure/event records. The host validates read-only tool names and date parameters. The model compares patterns and drafts a conclusion. If closure data is unavailable, report a correlation or unknown cause, not a claim that weather caused the decline. A strong answer identifies cited observations, timestamps, alternative explanations, and no unauthorized writes.

Exercise B — Predict the effect of temperature (5–10 minutes)

In the synthetic sampling lab, hold the candidate scores constant. Predict what happens when temperature changes from 0.2 to 1.8. Then test it. Why does a higher temperature not make factual claims more trustworthy?

Solution

At low temperature, probability concentrates on the highest score. At higher temperature, lower-ranked candidates gain relative probability and outputs become more varied. This changes diversity of sampling, not truthfulness of the underlying evidence. If the prompt lacks current status data, no temperature setting repairs that gap.

Exercise C — Independent transfer challenge (15–20 minutes)

You are asked to create an assistant that explains failed data-quality checks in a 100 TB hybrid platform. Draft a one-page design: user request, approved read-only tools, source selection strategy, context budget, response evidence format, failure handling, and three evaluation tests. Try independently before opening the rubric.

Hint

Think beyond a single model call. How will the application retrieve relevant context, bound cost, avoid exposing personal data, and decide that the evidence is insufficient?

Rubric and example outline

Excellent: 1) scoped goal; 2) allowlisted read-only quality/lineage/job tools with typed arguments; 3) targeted retrieval of relevant rules and recent failures, not every table; 4) token/time/tool budgets; 5) timestamps, IDs and distinction between observation and hypothesis; 6) escalation when evidence is missing; 7) tests for known failure, incomplete evidence and hostile text in a rule description. Compare this design against a deterministic rules engine before adding agent autonomy.

These written exercises are self-assessed in the browser. We cannot automatically verify the quality of open-ended reasoning without a separate evaluator; use the rubrics honestly. For expert training, you should also discuss your solution with a colleague or compare it against a tested implementation.
